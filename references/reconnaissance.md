# Reconnaissance: characterising a Claude Design export without loading it into context

> **Verified as of 2026-09-15** on one export (207 files, 17.8 MB, including a 12 MB standalone HTML and a 1.5 MB compiled bundle). File-format details — manifest keys, bundle header, `@dsCard` marker, bundler script types — were observed on that export. Re-verify on yours: `scripts/recon.py <tree>` prints what it finds and what it could not parse.

## Rules

- **Shell tools only.** `wc`, `head`, `grep -c`, `python3` parsing JSON headers. Never load a multi-megabyte file into a model's context; read its first 64 KB, its header line, or its counts.
- **Diff, do not summarise.** Anything described as "identical except N lines" gets diffed pairwise.
- **Docs are claims, not facts.** A readme in the recorded tree stated that a legacy component kit had been removed; 22 of its files were on disk, dead but present, and named in the bundle's hash map. Grep before believing.
- **Snapshots are history.** Claude Design has no version history; dated ZIP downloads in `~/Downloads` are the only one you have. Copy them somewhere durable with checksums before anything else. Comparing their manifests across dates also tells you whether the namespace is project-bound (it was stable across seven snapshots while content changed completely).

## Is this a design system, a prototype, or both?

Read `_ds_manifest.json`. Keys observed: `namespace`, `components[{name, sourcePath}]`, `cards[{path, group, viewport, subtitle, name}]`, `templates`, `tokens[{name, value, kind, definedIn}]`, `themes[{selector, label}]`, `globalCssPaths`, `fonts`, `brandFonts`, `startingPoints`, `hasThumbnailHtml`, `source`.

Then note what it does **not** enumerate. In the recorded case the manifest pointed at 27 component source files and 29 card pages, carried 397 token values inline — and referenced nothing under the screens directory, nothing under `assets/`, and not the demo-data file every screen loaded. A manifest-only import gets the library's identity and none of the working app. Whether the tree is "both" is decided by that gap.

## Source vs generated vs design-time input

| Pattern | What it is | Travel? |
|---|---|---|
| `uploads/pasted-<epoch>-0.png` | Reference screenshots pasted during design sessions | No — design-time input |
| `_ds_bundle.js` (`/* @ds-bundle: {…} */` header, IIFE, per-file `try{}` blocks) | Compiled output of the sources named in its `sourceHashes` | Yes if pages load it directly (they did: `<script src="…/_ds_bundle.js">` on every shell); otherwise regenerable |
| `_ds_manifest.json` | Compiled index, regenerated by the app's self-check from `@dsCard` first lines | Push it rewritten and self-consistent; expect the app to regenerate it |
| `.thumbnail` files | Captured renders | Negligible; keep |
| A multi-megabyte `.html` containing `<script type="__bundler/manifest">` (also `__bundler/template`, `__bundler/ext_resources`, `__bundler/page_order`) | A **standalone export**: a client-side bundler loader with all resources embedded as chunks | Not to the push — **but decode it before discarding**, see `vendoring.md` |
| A page carrying `<meta name="ext-resource-dependency">` tags and a resource-remapping shim | The prep source the standalone export was built from | Harmless; not a card; hardest thing in the tree to reconstruct by hand |

Detect the bundler loader from the first 64 KB: the loader script that reads `script[type="__bundler/manifest"]` appears near the top.

## Card markers

`grep -l '^<!-- @dsCard' **/*.html` on **first lines**. Their presence means the tree was authored for design-sync, the push route is correct, and the count should equal `cards` in the manifest (29 = 29 in the recorded case, once an earlier hand-tally was corrected). Group them by `group="…"`.

## Shells: diff pairwise

Bundle-loading pages in the recorded tree were 32-line shells: CDN scripts, the bundle, demo data, the shared helper, every screen module, then two lines naming the active route. 17 of 23 were byte-identical except the `@dsCard` line, the `<title>`, and the route lines — which is where the summary "only three lines vary" came from. A pairwise diff found a shell setting a **third** `localStorage` key on that same line (a role); the shape comparison the tool now runs found **four** such shells — two setting a role, two setting a fresh-account flag. A template-plus-route-table rebuilt from the common pattern would have dropped all of them silently.

`scripts/recon.py` clusters shells by their skeleton (the file minus the known varying lines), then compares the *shape* of those varying lines with every string literal blanked — an extra statement on a shared line changes the shape even when the line count is identical, which is exactly how the third key hid — and names the members whose shape differs. Diff those by hand. (The first version of the tool compared line counts and missed it; that is why this paragraph exists.)

## Assets: used, orphaned, missing

Collect every literal `assets/…` reference from the sources, pages, token CSS and any resource-dependency meta tags, normalising the relative depth (`assets/`, `../assets/`, `../../assets/`). Set-compare with the files present. Then grep explicitly for **dynamically constructed paths** — string concatenation or template literals containing `assets/` — which a literal grep misses. In the recorded case: 19 used, 4 orphaned (two documented as deliberately kept legacy marks, two genuinely unwired), 0 missing, and no dynamic construction.

## External hosts

Per file, every `https://<host>` literal. Expect CDNs in pages (React, Babel), font imports in token CSS, and icon-CSS loaders **compiled into the bundle** (grep the bundle too). Content links in demo data (social platforms, product domains) are not resources; separate them by whether they appear in `src`, `href rel=stylesheet`, `@import`, or `url()`.

## Dead code the bundle still names

Files provably unreferenced by any page may still be listed in the bundle header's `sourceHashes` (the compiler walked the folder before the files were orphaned). If they are absent at the destination, a validator sees missing sources and may recompile. Two honest options: push them (they are inert — 22 files, 237 KB in the recorded case, and that is what was chosen) or strip them from header **and** body deliberately. Document it as a reversal of the obvious call, made for a technical reason.

## Write it down

The audit document that carried the whole execution had six sections: design-system payload (what the manifest carries vs misses), screen inventory ordered by reconstruction difficulty with dependencies and self-containment, noise safe to drop (with "referenced by any screen?" per item), assets used/orphaned/missing, adherence tooling present, and transfer size before/after. Every later decision cited a section of it. Corrections were made to it three times as diffs replaced summaries; each correction is recorded in `HISTORY.md`.
